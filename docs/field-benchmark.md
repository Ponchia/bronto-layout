# Independent real-world layout benchmark — capture and labeling protocol

**Source checkout required:** `scripts/field-benchmark.mjs`,
`benchmarks/field-sites.v0.1.json`, and the associated capture/reviewer
workflow are developer/research tools. The installable npm package intentionally
omits the `scripts/` and `benchmarks/` directories. Clone the source repository
before following the commands below; installing just the CLI tarball is
insufficient for these workflows.

The controlled fixtures in `benchmarks/audit-controlled-*.json` are useful
regression tests but are **not** independent evidence of production accuracy.
This workflow separates a live browser capture from human ground truth so
neither labels nor negative cases can silently be inferred from the CLI.

## Dataset and evidence

`benchmarks/field-sites.v0.1.json` proposes 30 viewport states from five
first-party sites/routes: the personal website, Sense6 English, Sense6 Arabic,
Sense6 Learn and Chiara's portfolio preview, at 320, 360, 375, 430, 768 and
1280 CSS pixels. These sites are mutable. The manifest is a **planned cohort,
not 30 independently scored cases**. It uses an explicit HTTPS hostname
allowlist; URLs with credentials, query strings or fragments are rejected.

First validate the manifest, then capture the entire cohort or a subset:

```sh
npm run field:validate
node scripts/field-benchmark.mjs capture \
  --manifest benchmarks/field-sites.v0.1.json \
  --out reports/field-2026-10-12
node scripts/field-benchmark.mjs capture \
  --manifest benchmarks/field-sites.v0.1.json \
  --ids portfolio-375,sense6-ar-375 \
  --out reports/field-smoke-2026-10-12
```

On development boxes where Chromium cannot retain its security sandbox, do **not**
run public sites with `--no-sandbox` merely to obtain a score. Instead, manually
trigger the GitHub Actions **Manual first-party field benchmark capture**
workflow. Its disposable GitHub runner can use the documented opt-in Chromium
flag for the tightly allowlisted public websites. Supply `all` for the full
cohort or a comma-separated selection. Download the workflow artifacts and
review them locally; no ground-truth labels are generated by CI. Artifacts
may be visible to people with repository Actions access, so never use this
workflow for private pages or sessions.

Use a new output directory for every run. The collector never overwrites
existing evidence. Each case stores `audit.json`, a raw initial-viewport PNG,
and an index with content SHA-256 hashes, width, page URL, exit code, tool
version, Node version, browser user agent, final browser URL, source revision and timestamp. A screenshot is not an assertion that
the full page was visible: it covers the **initial viewport only**. The
reviewer must also scroll the real page and inspect interactive or below-fold
content. Incomplete browser observations are explicitly preserved and never
scored as negatives.

The browser sandbox stays enabled by default. Only the existing opt-in
`--no-sandbox`/`BRONTO_CHROME_NO_SANDBOX=1` escape hatch is available for
trusted isolated test environments, never recommended for unknown sites.
Screenshots can expose personal data: capture only permitted pages and do not
commit/share raw reports without review. The `reports/` path is gitignored.

## Prepare an independent-review worksheet

After downloading the captured artifacts, generate a human-readable review sheet that verifies the screenshot/report hashes without disclosing automated issue predictions as labels:

```sh
node scripts/field-benchmark.mjs review-packet \
  --captures reports/field-2026-10-12 --out reports/field-review-worksheet.md
```

The command never invents human judgments. It leaves checkboxes blank, flags incomplete evidence, and refuses to overwrite an existing worksheet. The reviewer must visit the rendered page as well as the initial-viewport screenshot, include below-fold/interactive states and manually supply evidence and intent. The worksheet deliberately does **not** copy predictions from the CLI report to avoid anchoring the reviewer.

## Offline visual contact sheet for independent reviewers

Before viewing any automatic audit findings, reviewers can open a locally generated **visual contact sheet** that displays the captured PNGs alongside only the source page, CSS viewport width, locale and capture-integrity state. It deliberately excludes detector findings, scores, inferred defects and generated human labels:

```sh
node scripts/field-benchmark.mjs review-gallery \
  --captures reports/field-2026-10-12 \
  --out reports/field-2026-10-12/review-gallery.html
```

Open `review-gallery.html` in your browser **after extracting the capture archive**. It is an offline, dependency-free HTML file, with local relative image links, a restrictive content-security policy and no JavaScript or external tracking. Viewport screenshots appear on review cards; a second collapsible image appears when optional bounded page evidence was captured. Image/report SHA-256 digests are verified before generation, and missing, tampered or non-PNG screenshots are marked unsafe instead of presented as valid. Captures are never overwritten, and linked image paths cannot escape the extracted capture directory through traversal or symlinks. The report deliberately hides `audit.json` predictions until the independent review is complete.

New manual GitHub Actions field captures automatically include both `review-gallery.html` and `review-worksheet.md` in the same seven-day artifact when a capture index exists, including for partially failed runs. They do not require or generate labels. For historical archives, the commands above let reviewers generate the same files locally without a new website capture. Keep the gallery and its referenced `cases/` folders together, since it does **not** embed the potentially large PNG files.

**Important:** a screenshot is only the browser state already captured at the recorded width. Reviewers must still inspect the live rendered site, including scrolling, content loaded on demand and interactive conditions. The contact sheet is an aid to *human* labeling, not evidence that the page is correct; only human-origin labels belong in `field-manual-labels.json`.

## Optional bounded below-the-fold evidence

For reviewable pages, request an additional **bounded document screenshot** without replacing the original viewport PNG or changing any automatic detector conclusions:

```sh
node scripts/field-benchmark.mjs capture \
  --manifest benchmarks/field-sites.v0.1.json \
  --ids portfolio-375 --full-page-evidence \
  --out reports/below-fold-review-2026-10-12
```

For external allowlisted pages on a shared development host, use the manual GitHub Actions capture workflow with `full_page_evidence=true` on a disposable runner rather than disabling Chromium's sandbox locally. The option also works with `--frame-inventory` when additional frame coverage evidence is useful. Existing capture defaults are unchanged.

This uses Chromium `Page.getLayoutMetrics` (CSS dimensions) and `Page.captureScreenshot` with `captureBeyondViewport` and an explicit top-left clip. The evidence rectangle is bounded to **4,096 CSS px in width**, **6,000 CSS px in height**, and **12 million CSS pixels of area**. Pages larger than that are partially captured and marked as `bounded-top-left-rectangle`; smaller pages are recorded as `rendered-document-rectangle`. Both records describe a **single observed rendered state**, not complete CSS correctness. Pixels after the cap, lazy-loaded content, animations, interactions, virtual scrolling, closed shadow roots and iframe internals are not certified.

The capture index records a separate image path, SHA-256, observed geometry, and `fullPageTruncated` status. Review worksheets disclose the truncation and verify that file's digest; scoring excludes cases with a requested but missing/tampered bounded image rather than assigning them true negatives. Even a valid, non-truncated screenshot **does not replace** independent review of the running page, below-fold or interactive states. Existing 30-state captures without this opt-in remain valid viewport-only evidence and are never retroactively described as whole-document screenshots.

Standalone use:

```sh
bronto-layout audit --url http://localhost:5173/ --width 375 \
  --json --compact --evidence-dir reports/screens --full-page-evidence
```

The CLI refuses `--full-page-evidence` without `audit --evidence-dir`, and does not support screenshot capture for baseline comparisons. No screenshot imagery is read by the automatic detector to infer bugs.

## Optional frame-evidence capture and scoring protection

For an allowlisted public-site capture, enable `--frame-inventory` only when frame coverage is relevant:

```sh
node scripts/field-benchmark.mjs capture \
  --manifest benchmarks/field-sites.v0.1.json \
  --ids chiara-preview-375 --frame-inventory --out reports/chiara-frame-2026-10-12
```

The exact case IDs are defined by the manifest. On a shared devbox that cannot retain the Chromium sandbox, run the manual GitHub Actions **Manual first-party field benchmark capture** workflow instead, with its `frame_inventory` option, inside the allowlisted disposable runner. Do not disable the browser sandbox to inspect an arbitrary public URL on a shared host.

Chromium's frame-tree and DOMSnapshot data show **which frame documents were observed in a snapshot**; they do not establish whether their inner contents rendered correctly. The audit retains `embedded-frame-uninspected` review warnings. Frame IDs are ephemeral, captured document counts are bounded, and HTML/canvas/shadow/paint-order completeness is not inferred. URL credentials, query strings and fragments are stripped from frame inventory output.

For captures made with the current CLI, `summary.verified=false` also covers **known uninspected iframe interiors**. `summary.supportedScopeMeasured=true` means the supported top-document/open-shadow walk completed, allowing the raw capture to remain intact; field *accuracy scoring* still excludes these frame-bearing states. Historical audit JSON without the new boolean is supported by the field capture and scorer compatibility checks.

**Capture integrity and diagnostic completeness are distinct.** The capture index may record `complete: true` when a screenshot and top-level audit were successfully acquired, even if an iframe was not inspected. `contentCoverage` documents that limitation; the field scorer excludes reviewed cases with `known-uninspected-content` from whole-page detector accuracy denominators. Historical captures without `coverage.status` still use `embeddedFrames` to avoid silently counting missing interior observations as true negatives. The scorer reports these separately under `coverageExcluded`. Labels are never inferred from Chromium data.

## Optional offline human review console

An independent reviewer can use the generated `review-console.html` **after extracting the capture archive** rather than typing JSON by hand. The script-free `review-gallery.html` stays available for reviewers who prefer a static contact sheet. The console is a separate, explicitly opened HTML file with source-hash-locked inline JavaScript. No remote scripts, trackers, `fetch` requests, `localStorage`, or automatic uploads are used. Its only outbound action is an ordinary live-site link you choose to open; the console itself handles case inputs locally. CSP disables script injection, connections, frames and forms.

```sh
node scripts/field-benchmark.mjs review-console \
  --captures reports/field-2026-10-12 \
  --out reports/field-2026-10-12/review-console.html
```

Every case starts `pending`. The console shows the case ID, captured width, source link without query tokens, hash-verified initial/bounded screenshots, and explicit incomplete/iframe coverage caveats. A reviewer may select `reviewed` **only if capture evidence passed integrity checks** and they have independently inspected the screenshot and live rendered page. That choice requires their identifier, date, rationale, both attestations and independently selected detector codes; an empty list is an explicit judgment, not a default. `unreviewable` requires a reviewer/date/rationale but carries **no** expected detector codes. Failed-integrity cases cannot be marked reviewed. Unknown iframe interiors remain excluded from subsequent **whole-page** field accuracy scoring even if a screenshot hash is valid.

Click **Export human labels JSON** to download a JSON file into your local browser downloads; it contains pending entries for unreviewed cases and explicit decisions for completed ones. The browser validates declarations before exporting; it never quietly promotes pending to reviewed. **Import existing reviewer JSON** lets you resume an earlier local draft. Imports require the same dataset/case IDs and valid states; unknown or malformed content is rejected before modifying the form. **Partial imports merge by case ID:** only cases actually named in the imported JSON are replaced; in-progress reviews for omitted cases remain untouched. A full-cohort import intentionally replaces every case. The console tells you how many cases were imported and how many were left unchanged. It does not overwrite files or retain inputs across reloads; **export before closing the tab**. Keep screenshots and reviewer exports private where appropriate.

The exported JSON follows the same validated schema as `review-label-template` and works with `review-progress` and `score`. Neither the console nor the initial human reviewer declaration proves independence or design correctness. Automatic Bronto audit predictions are not included in the page, and the code does not read them to suggest labels. Any actual reviewer must assess the site **before reading** `audit.json`.

## Start a human-review labels draft without inventing negatives

Manual first-party field capture artifacts now include `review-labels-draft.json`,
with **one pending entry per captured state** (no positive or negative labels).
The review gallery and worksheet are deliberately independent from model or
detector predictions; reviewers should inspect screenshots **and the actual
rendered page**, including below-fold and relevant interactions, before reading
`audit.json`. The draft only records case IDs, so it is safe to generate before
human review:

```sh
node scripts/field-benchmark.mjs review-label-template \
  --captures reports/field-2026-10-12 \
  --out reports/field-manual-labels.json
node scripts/field-benchmark.mjs review-progress \
  --captures reports/field-2026-10-12 \
  --labels reports/field-manual-labels.json
```

The draft starts as `{ "id": "...", "reviewStatus": "pending" }`. This is
**not** a reviewed negative case. To finish an entry, a human must set
`reviewStatus` to `reviewed`, supply the required `reviewer`, `reviewedAt`,
`rationale`, `reviewedScreenshot: true`, `reviewedRenderedPage: true`, and
independently determined `expectedMeasured` and `expectedReview` arrays. For
an unreviewable case, use `reviewStatus: "unreviewable"` with a reviewer,
review date and explanation, omitting all expected detector arrays.

`review-progress` validates these declarations and screenshot/report hashes,
shows pending/reviewed/unreviewable and evidence-unsafe counts, and **never
reads detector findings or computes quality scores**. A pending record carrying
an expected label or reviewer attestation is rejected; the status must change
to `reviewed` and satisfy the full validation schema first. The command never
modifies a review file. `score` excludes pending/unreviewable entries and
refuses accuracy scoring when no independently reviewed entries remain; with
`--assert`, any unfinished capture also causes a nonzero exit.

## Label independently

Before consulting `audit.json` findings, a named human reviewer should
inspect the page, screenshots, DOM and computed styles, and record whether
each supported detector category actually applies in the observed state.
Separate intentional design decisions from genuine failures and mark cases
unreviewable when reliable judgment is not possible. Record `reviewer`,
`reviewedAt`, `rationale`, and the page/width/state. `reviewedAt` must be
an actual ISO `YYYY-MM-DD` calendar date, including correct leap-day handling;
impossible dates are rejected rather than silently normalized by JavaScript.
This checks record consistency, not whether someone actually reviewed the page.
Do not use the output of Bronto Layout to generate the expected labels.

Prefer `review-label-template` for captured cohorts; alternatively copy
`benchmarks/field-labels.template.json` to an untracked file. For every
reviewed case, add a record like:

```json
{
  "id": "portfolio-375",
  "reviewStatus": "reviewed",
  "reviewer": "Human reviewer identifier",
  "reviewedAt": "2026-10-12",
  "rationale": "Document concrete visual/DOM evidence and intentional exceptions.",
  "reviewedScreenshot": true,
  "reviewedRenderedPage": true,
  "expectedMeasured": [],
  "expectedReview": []
}
```

The empty arrays above are a **schema illustration**, not labels for that
site. For unreviewable cases, omit expected arrays and explain why.
Missing case labels remain pending, not implicitly healthy. The review
attestation is a protocol requirement rather than automated proof that the
review was independent.

## Score separately

```sh
node scripts/field-benchmark.mjs score \
  --captures reports/field-2026-10-12 \
  --labels reports/field-manual-labels.json \
  --json --report reports/field-score.json
```

Per-detector confusion matrices reuse the controlled benchmark scoring
semantics. Reviewed cases with incomplete or changed screenshot/report hashes
are excluded and explicitly counted. No reviewed cases means no score. A
missing positive denominator yields `null`, never a fabricated 100% score.
`--assert` refuses missing/unreviewable browser evidence and unreviewed
case coverage, and fails on classification mismatches.

Before competitive claims, broaden beyond first-party sites with permission,
obtain genuinely independent labels, compare Snug and other tools on identical
states, browsers and viewports, and report both false positives and missed
problems. We do not currently have that external comparison.
